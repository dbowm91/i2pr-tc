## 3. Raw-SAM factory and client ownership

```
managed app runtime composition (M004, not built here)
    |
    |  implements SamConnectionFactory
    |  open_sam_connection() -> one raw SAM protocol stream
    v
SamClient<F>                     crates/i2pr-tc-i2p/src/sam.rs
    owns: SamIdentity (Destination + session id), SamLimits, SamTimeouts,
          Cancellation (shutdown), SessionState {available, created,
          negotiated, in_flight}
    |
    |  every operation: begin() -> bounded(deadline, cancellation) -> end()
    v
SAM v3 octets on that stream
    HELLO / SESSION CREATE / NAMING LOOKUP / STREAM CONNECT / STREAM ACCEPT
```

- Connection loss never destroys the torrent identity: `SamIdentity` holds the
  application Destination, and `SESSION CREATE` is attempted once per session id.
- A SAM session failure marks the transport unavailable and fails dependent
  operations; `close()` cancels in-flight work, waits a bounded time for
  unwinding, then reports.
- No retry loop exists inside the client. `ensure_session` is documented as a
  single bounded attempt precisely so an unavailable service cannot produce a
  reconnect storm, and callers own re-establishment policy.
- `SamIdentity` takes the private destination as an injected value. It reads no
  filesystem secret and no environment variable; persistence policy belongs to
  the M004 composition layer.

## 4. SAM command/reply matrix

| Command | Exact octets | Result vocabulary mapped | Failure maps to |
| --- | --- | --- | --- |
| `HELLO` | `HELLO VERSION MIN=3.1 MAX=3.1\n` | `OK` + `VERSION=` must parse; `NOVERSION` | router result → `Session`; malformed/absent version → `Protocol` |
| `SESSION CREATE` | `SESSION CREATE STYLE=STREAM ID=<id>\n` | `OK`; `DUPLICATED_ID` tolerated only for a session this client created | `Session` |
| `NAMING LOOKUP` | `NAMING LOOKUP NAME=<name>\n` | `OK` + `DESTINATION=`; `KEY_NOT_FOUND` | `Session` |
| `STREAM CONNECT` | `STREAM CONNECT ID=<id> DESTINATION=<b64> PORT=<n> SILENT=false\n` | `OK`, remainder is raw data | `Session` |
| `STREAM ACCEPT` | `STREAM ACCEPT ID=<id> SILENT=false\n` | `OK` + `DESTINATION=`, remainder is raw data | `Session` |

- `STREAM FORWARD` is not implemented anywhere. A transcript test asserts the
  client's complete written-octet set never contains it.
- `port` is always carried explicitly, including `PORT=0`, which the peer path
  passes and routers treat as "no port". The client does not special-case it.
- Bounds: line, total reply, token, value, and option count, with
  `SamLimits::strict()` giving a deliberately tight profile so every rejection
  path is reachable in tests and under fuzzing.
- Errors: non-UTF-8, unknown reply kind, unknown result, line or total overflow,
  empty key, malformed or unterminated quoted value, too many `KEY=VALUE` lines,
  a Destination that fails base64 or falls outside 387..=8192 bytes, and
  non-decimal or overflowing version numbers are all typed rejections. None
  panic and none allocate unbounded.

## 5. Tracker HTTP fingerprint, before and after

Before, for every announce:

```
GET /announce?passkey=secret&info_hash=%AB...&peer_id=%01%02... HTTP/1.1\r\n
Host: tracker.i2p\r\n
Accept: */*\r\n
Connection: close\r\n
User-Agent: i2pr-tc/0.1\r\n
\r\n
```

After (golden test `golden_announce_request_bytes_omit_any_version_fingerprint`):

```
GET /announce?passkey=secret&info_hash=%AB...&peer_id=%01%02... HTTP/1.1\r\n
Host: tracker.i2p\r\n
Accept: */*\r\n
Connection: close\r\n
\r\n
```

Omission was qualified, not merely preferred. qBittorrent's Anonymous Mode
resets the header to an empty string and keeps announcing against the same
trackers, and the I2P BitTorrent specification documents announce parameters
without mandating the header. A deployed client therefore does not need it, so
removing it costs interoperability nothing and removes a fingerprint for free.

`TrackerIdentity::Fixed` remains as an operator escape hatch for a private
tracker that rejects headerless announces. It accepts one stable, non-versioned
value and rejects anything version-shaped, so configuration cannot reintroduce
the fingerprint this corrective removed.

The BEP 10 `v` key is also gone from the extension handshake, matching
qBittorrent's Anonymous Mode, which also ships with no client version in it.

## 6. State-lock and storage ownership

Before:

```
TorrentRuntime
  torrents: Mutex<BTreeMap<TorrentId, TorrentRuntimeState>>
              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
              held across store_piece_with_cancellation
              (Storage::open, prepare, write, atomic_json of the catalog record)

PersistentTorrentService
  state: Mutex<State>
          ^^^^^^^^^
          held across the same filesystem work plus atomic_json
```

Both were global head-of-line blockers, and `Storage::disk` is per-`Storage`
instance, so two handles over the same payload root did not exclude each other.

After:

```
TorrentRuntime
  torrents: Mutex<BTreeMap<TorrentId, Arc<Mutex<TorrentRuntimeState>>>>
              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
              held only to clone an Arc

  per torrent: Mutex<TorrentRuntimeState>
    reserve_piece()  -- assembly under this lock, buffer moved OUT,
                         (piece, generation) recorded as a reservation
    [ no torrent lock, no catalog lock held here ]
    store_piece_with_cancellation()   -- filesystem work
    commit_piece()    -- under the torrent lock again; commits only if the
                         reservation is still the authority

PersistentTorrentService
  state: Mutex<State>
          ^^^^^^^^^
          short in-memory mutations only
  payloads: Arc<Storage> per payload root, cached
            so Storage::disk really does serialize per torrent
  commit_catalog_write(): durable record written outside the lock, with a
          revision check so a concurrent mutation is retried rather than lost
```

No lock in either crate is held across any filesystem read, write, hash,
recheck, or catalog-record replacement.

## 7. Persistence race and cancellation matrix

| Case | Test | Outcome |
| --- | --- | --- |
| peer disconnect after assembly, before persistence | reservation is taken before any I/O; a missing request is refused | reservation released, piece retryable |
| choke while persistence is in flight | generation unchanged; the reservation commits and the piece is verified | `Verified` |
| stop while persistence is in flight | `Stop` re-registers and mints a new generation | `Ok(false)`, verified bytes stay 0 |
| remove while persistence is in flight | torrent leaves the catalog | `Ok(false)`, `get` → `NotFound` |
| duplicate block during persistence | second reservation for a piece already in flight | `Err(Conflict)` |
| cancellation before storage begins | checked before reservation | `Err(Cancelled)`, executor never ran |
| cancellation during storage work | storage call is cancellable; reservation still authoritative | `Err(Cancelled)`, piece reset |
| storage/hash failure | write fails; reservation released and piece reset | error surfaces, piece retryable, retry then succeeds |
| successful storage after stop | generation mismatch | `Ok(false)`, no resurrection, no double count |
| two torrents persisting concurrently | no global lock spans either write | second torrent completes while the first is parked inside the blocking write |

## 8. Multi-torrent concurrency evidence

`p7_one_torrents_disk_write_does_not_block_another_torrents_state` uses a gated
executor that parks a job inside the blocking storage layer and only releases it
when the test says so. While parked, a second torrent completes its own piece
end to end through the ordinary synchronous path. This is a property of the
lock structure, not a timing observation: if any global lock were still held
across the first torrent's write, the second call could not return.

`p9_bounded_executor_applies_backpressure_instead_of_queueing` shows the bound:
with capacity one, a second submission is refused outright while the first is
parked, and the refused torrent keeps its piece so the work stays retryable.

## 10. Defects the magnet qualification exposed

Three latent wire defects, each of which had silently disabled extension
exchange with any real peer. No existing test caught them because no test fed
the client's own handshake back through the parser it ships.

1. `encode_extension_handshake` declared `8:i2p_pex` for the 7-byte string
   `i2p_pex`. The client's own extension handshake was unparseable by any
   conformant parser.
2. `metadata_size` was written after the dictionary containing it had already
   been closed, so the handshake could not round-trip.
3. The reply-kind parser treated `HELLO REPLY` as a `STATUS` reply, so every
   SAM handshake failed.

Each is now covered by `extension_handshake_advertises_support_without_a_version_fingerprint`,
which asserts both handshake shapes round-trip through the same parsers the
client uses on a peer.

## 10a. Correction: defects the live-router run exposed

The live matrix in §9 was run on 2026-10-07 against i2pd 2.61.0. It found four
defects that no transcript test could have found, because every transcript
fixture had been written to match the client's own assumptions rather than a
real service's answers. Every unit test passed throughout; all four were live
only.

| Defect | Symptom against a real service | Fix |
| --- | --- | --- |
| `SESSION CREATE` omitted `DESTINATION=` | every attempt answered `INVALID_KEY`; no session could ever be created | `SamSessionDestination` makes the parameter mandatory, as `TRANSIENT` or injected key material |
| base64 used the standard alphabet | i2pd substitutes `-` and `~` for `+` and `/` at index 62 and 63 (`libi2pd/Base.cpp`, `T64`); a standard-alphabet value is rejected rather than decoded, so no real Destination could be parsed or dialled | the SAM wire codec uses I2P's alphabet, padded, and rejects `+`/`/` rather than accepting a form no service decodes |
| `NAMING LOOKUP` read `DESTINATION=` | i2pd answers `NAMING REPLY RESULT=OK NAME=… VALUE=…`; waiting for `DESTINATION` blocked until the lookup deadline expired | `nam_lookup` reads `VALUE` |
| `STREAM ACCEPT` read a `DESTINATION=` line | i2pd writes the connecting peer's destination alone on the line after the status line, with no option key; reading it as `KEY=VALUE` consumes the peer's first bytes instead | `stream_accept` reads one bare destination line |

The supporting facts were confirmed against i2pd 2.61.0 source at tag `2.61.0`
(`libi2pd/Base.cpp`, `libi2pd/Identity.cpp`, `libi2pd_client/SAM.cpp`,
`libi2pd_client/SAM.h`) and against the running bridge.

Two behaviours of `DESTINATION=` are recorded because they constrain what a
production client must do, and neither is this client's decision:

- The **decoded length is the service's contract, not the client's.** i2pd
  rejects a 387-byte Destination, a 32-byte key, and a 483-byte blob, and
  accepts only the 663-byte private-keys blob it emits itself.
  `SamSessionDestination::validate` therefore checks only that the value can be
  carried on one command line and decoded, and leaves the rest to the service's
  own `INVALID_KEY`.
- A **transient identity is per-connection.** Two `NAMING LOOKUP NAME=ME` calls
  on the same client returned different Destinations, because each raw
  connection creates its own transient session. A client that must be dialled,
  or that must persist its identity, has to inject key material, which the live
  harness now qualifies separately via `I2PR_TC_LIVE_SESSION_KEYS`.

`SamIdentity` was reshaped to match. It previously accepted an optional
Destination that it never put on the wire, which let a caller believe it had
pinned an identity with the router when it had not. It now holds only the
session-creation form, reports `has_persistent_keys`, and always reports a
documented placeholder local hash: reconstructing a Destination — and therefore
its hash — from key material is outside this crate. A caller needing the real
local hash resolves it from the router with `NAMING LOOKUP NAME=ME`.

## 13. M004 unblock decision

**M004 is unblocked.**

- The application-side SAM contract is implemented and transcript-tested, with
  no router type named anywhere in this repository.
- The only missing production piece is the M004 composition that supplies
  `SamConnectionFactory` from the managed app runtime. That is exactly the seam
  this plan was scoped to leave open.
- The live interoperability matrix in §9 has since been run against i2pd
  2.61.0. It found and fixed the four defects in §10a, which is precisely why
  it was worth running before M004 built on this client.
- What remains for M004 is narrower: the three §9 cases that need a registered
  name, a second peer, and a tracker URL, plus a production decision on
  injecting and persisting key material, since a transient identity is
  per-connection and cannot be dialled.
